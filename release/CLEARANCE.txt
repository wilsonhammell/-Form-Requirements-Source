PDF Requirement Designer - security review pack
===============================================
Generated 2026-09-10 from package-lock.json and the shipped build.

WHAT THIS IS
------------
A browser tool for marking up PDF forms and exporting a requirements JSON
and an Excel workbook alongside the PDF. It is a static web page. There is
no backend, no database and no account system.

NOTHING IS DOWNLOADED OR INSTALLED
----------------------------------
This package is the finished build. No package manager runs, at install
time or at run time. No code is fetched from anywhere. Copying the files
into place is the entire deployment.

There is no package.json, no package-lock.json and no node_modules in this
package, so there is nothing here for npm or any other tool to resolve.
The full file list, with a SHA-256 for each, is at the end of this
document.

WHAT ACTUALLY RUNS, AND WHERE
-----------------------------
The application is JavaScript that runs inside the user's browser. The
browser is the only thing executing application code.

The included serve.ps1 / serve.py / serve.mjs are file servers, not the
application. They read files from their own folder and return them over
HTTP. They do not parse or execute any of the JavaScript they serve. They
exist only because a browser will not load an ES module or read a local
JSON file over file://, so the files need an HTTP origin.

If this folder is hosted on an existing internal web server, all three are
unused and can be deleted.

WHAT IS NOT IN THE BUILD
------------------------
The source repository's lockfile lists 296 packages: 118 reachable at run
time and 178 build toolchain. The build discards everything the
application does not actually reach, which is why the list above is far
shorter.

Six packages in the dependency tree are marked deprecated by their
publishers: fstream, glob 7, inflight, lodash.isequal, rimraf 2 and
uuid 8. All but uuid arrive through the Node.js code paths of exceljs,
which a browser never takes. Verified against the shipped bundle:
fstream, glob, inflight, rimraf, archiver and unzipper contribute nothing
to it. uuid is present, inside the exceljs browser bundle.

KNOWN ADVISORIES, AS AT 2026-09-10
----------------------------------
Disclosed here rather than left to be discovered.

1. pdfjs-dist 5.7.284 - HIGH - GHSA-hq66-cqwq-w95j
   "Arbitrary JavaScript execution upon opening a malicious PDF."
   Affects >=5.6.83 <6.2.108. Fixed in 6.2.108, which is a major version
   change from the 5.x line this build uses.

   Relevance: the core action of this application is opening a PDF chosen
   by the user, so this advisory is directly on the main path and should
   not be treated as theoretical. The exposure is bounded by the fact that
   the code runs in the browser sandbox with no server, no stored
   credentials and no outbound network access, and that users open forms
   they already hold rather than files from untrusted sources. That
   reduces the impact; it does not remove the finding.

   Status: not yet remediated. Upgrading to the 6.x line is the fix and
   needs testing against the existing forms before it can ship.

2. uuid 8.3.2 - MODERATE - GHSA-w5hq-g745-h8pq
   "Missing buffer bounds check in v3/v5/v6 when buf is provided."
   Reached only through exceljs. The published remediation path downgrades
   exceljs to 3.4.0, which is a breaking change. The affected code path
   takes a caller supplied buffer, which this application never does.

DATA HANDLING
-------------
  - The application makes no outbound network calls.
  - PDFs opened by a user are read in that user's browser and are never
    uploaded or stored on a server.
  - Exports (PDF, JSON and Excel) are ordinary browser downloads.
  - The only files it reads are dbFields.json and systemFields.json from
    its own folder.
  - No cookies, no analytics, no telemetry, no external fonts or CDNs.

CONFIGURATION DATA
------------------
dbFields.json and systemFields.json are configuration, not code. They hold
field identifiers and labels, no customer or account data. The application
fetches them at run time with cache: no-store, so they are read fresh on
every page load.

They are intended to be edited in place after deployment. Changing them
needs no rebuild, no redeploy and no restart: edit the file, reload the
browser. Whoever hosts this should expect these two files to change and
should allow a named person or group to write to them.

Consequence for the manifest below: a SHA-256 recorded here for either of
those two files describes them as shipped. Once they are configured, their
hashes will differ, and that is expected rather than a sign of tampering.
Every other file in the manifest should always match.

WHAT A SCANNER WILL AND WILL NOT SEE
------------------------------------
Composition analysis tools work from package manifests. This folder has
none, by design. A scan of the deployed files will find little or nothing,
and that is expected rather than reassuring.

The bundler discards package names, rewrites internals and keeps only
reached code. This document and the SBOM are the record of what went into
the build; they cannot be reconstructed by inspecting the output, and
should be treated as the authoritative inventory.

NETWORK EXPOSURE
----------------
Default: serve.ps1 registers http://localhost:<port>/ and is reachable
from the local machine only. It needs no administrator rights and no
firewall change.

Note for anyone reviewing a port scan: HttpListener is served by the
Windows kernel HTTP driver (http.sys, PID 4), so netstat shows the port on
0.0.0.0 rather than 127.0.0.1. http.sys routes a request only if its Host
header matches the registered prefix. Measured:

    Host: localhost      -> 200, serves the app
    Host: 127.0.0.1      -> 400, refused
    Host: <machine ip>   -> 400, refused
    Host: <machine name> -> 400, refused

A client on another machine necessarily sends the ip or the machine name,
so it receives 400 and never reaches any content.

serve.py and serve.mjs bind the 127.0.0.1 socket directly. Both accept an
optional --lan flag which binds all interfaces with no authentication;
that is off unless explicitly requested on the command line.

RUNTIME REQUIREMENT
-------------------
None. Nothing has to be installed.

The default launcher uses Windows PowerShell 5.1 and .NET's
System.Net.HttpListener, both part of a standard Windows 10/11 install.

Start.cmd passes -ExecutionPolicy Bypass. That applies to that single
process only. It alters no machine or user setting, requires no elevation,
and does not persist. It is needed because a file that arrived by download
or email carries a mark-of-the-web flag, and the default RemoteSigned
policy refuses to run such a script.

Two equivalent servers are included for sites that would rather use an
existing approved runtime. Both are standard library only:

  serve.py     Python 3.x   http.server, socketserver, mimetypes, socket
  serve.mjs    Node 18+     node:http, node:fs, node:path, node:url
